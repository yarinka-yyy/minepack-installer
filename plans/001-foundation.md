## Зачем и что будет готово

Проверить основной путь продукта на маленьком настоящем пакете: закреплённый Packwiz-релиз → `.mrpack` → загрузка и проверка → отдельный Game Directory → профиль официального Launcher. Приложение должно уметь повторно проверить и восстановить свои файлы, а при удалении сохранить пользовательские данные. Это фундамент, на котором позже можно собирать полную подборку модов и расширять UI.

**Граница результата:** локальный рабочий прототип, а не публичный релиз или финальная сборка из 20–30 модов. Самозапускаемая сборка Windows должна открываться; программные проверки должны проходить. Фактический запуск Minecraft через аккаунт и ручная оценка поведения отмечаются отдельным итогом, если их нельзя выполнить автоматически.

## Неподвижные правила из спецификации

- Packwiz — исходник автора; `.mrpack` — неизменяемый артефакт версии. Установка не подбирает `latest` на лету.
- `.mrpack` лежит в ZIP, `modrinth.index.json` описывает относительные пути, HTTPS-источники, SHA-512 и Minecraft/Fabric versions. Учитывать `overrides` и `client-overrides`.
- Не трогать vanilla `.minecraft`, учётные данные и чужие профили. У сборки отдельный versioned Game Directory.
- Скачивать максимум 5 файлов одновременно, во временный каталог, с повтором сетевых ошибок и учётом `Retry-After`; сверять SHA-512 **до** размещения. Не допускать выхода ZIP/manifest path за пределы instance, включая absolute/drive paths, `..` и повторные пути.
- Не активировать новый профиль до успешной проверки staging. Ошибка не меняет последний рабочий instance. Repair исправляет только managed files; Uninstall сохраняет `saves`, screenshots и прочие unmanaged files.
- Launcher integration пока не подтверждена: [Fabric CLI](https://wiki.fabricmc.net/install) создаёт профиль, но [официальное руководство Fabric](https://wiki.fabricmc.net/player:tutorials:install_mcl:windows) задаёт Game Directory вручную. В [исходнике Fabric Installer](https://github.com/FabricMC/fabric-installer/blob/master/src/main/java/net/fabricmc/installer/client/ProfileInstaller.java) профиль создаётся без `gameDir`. Автоматическое редактирование Launcher-файлов требует отдельного исследования и проверки; Launcher должен быть закрыт.

## Шаги

### 1. Поднять минимальный репозиторий и решение

Повторить preflight: в `app/` только `plans/`. Создать Git в `app/`, `origin` на указанном SSH URL, `.gitignore` для `bin/`, `obj/`, `artifacts/`, локальных логов, staging и пользовательских данных. Создать `MinePack.slnx`, WPF `src/MinePack.Installer` (`net10.0-windows`), библиотеку `src/MinePack.Core` (`net10.0`) и консольную проверку `tests/MinePack.Smoke` (`net10.0`). Проект UI ссылается на Core, smoke — на Core. `README.md`: назначение, структура, точные команды build/smoke/publish, необходимые инструменты и граница тестового пакета. Без DI-контейнера и дополнительных пакетов «на будущее».

**Проверка:** `dotnet build MinePack.slnx -c Release` → код 0; `git rev-parse --show-toplevel` из `app/` → абсолютный путь `app/`; `git remote get-url origin` → указанный SSH URL.

### 2. Сделать реальный маленький Packwiz test pack

Исследовать **на момент исполнения** актуальную стабильную Minecraft-версию, Fabric Loader и Fabric API через первичные метаданные Fabric/Modrinth. Кандидат на дату плана — Minecraft `26.2`: [Fabric docs](https://docs.fabricmc.net/players/installing-fabric/windows) и [страница Fabric API](https://modrinth.com/mod/fabric-api) отмечают поддержку; окончательно подтвердить API metadata, статус release, dependencies и доступность Fabric Installer. Для теста достаточно Fabric API и его обязательных зависимостей; не добавлять Mod Menu или декоративные моды без нужды. Если `26.2` не проходит проверки, выбрать ближайшую более раннюю стабильную версию и описать причину в `README.md`; существенный откат требует решения пользователя.

Создать Packwiz project в `pack/test-pack/` с точными версиями, экспортировать `.mrpack` в `releases/test-pack/`; записать SHA-512 `.mrpack` и идентификаторы Minecraft/Fabric/Fabric API в release metadata/README. Не включать чужие JAR в EXE или ZIP overrides без проверки права распространения. Не использовать dynamic latest при установке. Если Packwiz не может экспортировать выбранный мод из разрешённого URL, остановиться и сообщить точную причину.

**Проверка:** из `app/pack/test-pack/` запустить `packwiz modrinth export -o ../../releases/test-pack/test-pack-0.1.0.mrpack` → код 0; открыть архив штатным `ZipArchive`, убедиться в наличии `modrinth.index.json`, правильных зависимостях и SHA-512 у каждого downloadable file; повторный экспорт из тех же исходников должен дать тот же набор версий и хешей файлов (побайтовое совпадение ZIP не требовать).

### 3. Реализовать безопасный установочный движок

В Core реализовать перечисленные в разделе «Разрешённые пути» классы по их прямым обязанностям. Использовать `System.Text.Json`, `ZipArchive`, `HttpClient`, `SHA512` и файловые API .NET. Архив и JSON — недоверенный ввод: ограничить извлечение только нужными override-каталогами, отвергать дубликаты/case-insensitive столкновения путей, reparse-point/symlink escape, неподдерживаемую структуру и неизвестный installer schema version. HTTPS allowlist соответствует проверенным источникам релиза; каждый redirect также проверять. Не исполнять скачанные mod JAR. В smoke подставлять тестовый `HttpMessageHandler`, не ослабляя production HTTPS-валидацию.

Новый instance создавать в отдельном versioned каталоге, затем после полной сверки помечать готовым. Отмена/ошибка оставляют предыдущий рабочий instance и профиль нетронутыми. Повтор после ошибки начинает с проверенных файлов, не доверяя недопроверенному partial download. Отображать прогресс и понятный код причины. Записать локальный manifest только после успешной установки.

**Проверка:** smoke-проект проверяет валидный тестовый архив, отклонение `../`, absolute/drive path, неверного SHA-512, неразрешённого URL и конфликтующих путей; имитирует сбой загрузки и убеждается, что прежний instance/маркер активности не изменён. `dotnet run --project tests/MinePack.Smoke -c Release` → все PASS.

### 4. Добавить Repair, Uninstall и логи

Repair читает локальный manifest, пересчитывает SHA-512 managed files и докачивает/заменяет только отсутствующие или повреждённые. Не удалять неизвестные файлы. Uninstall снимает только собственный профиль (когда безопасный способ подтверждён) и удаляет только managed files/metadata; при непустом instance сохраняет `saves`, screenshots и unmanaged файлы, показывает оставшийся путь. Структурированный локальный лог включает версии, этапы, пути, URL origin, HTTP/retry/hash и причину ошибки; не пишет токены или поля аккаунта. Кнопка экспорта диагностического отчёта.

**Проверка:** smoke-проект повреждает managed file и добавляет `saves/world`, затем Repair возвращает ожидаемый hash и сохраняет world; Uninstall удаляет управляемое и сохраняет world. Все сценарии PASS.

### 5. Проверить и подключить официальный Launcher

До записи изучить текущие варианты Launcher data directory/profile files и поведение Fabric Installer CLI; проверить на **одноразовых копиях** JSON, что можно создать только свой профиль с собственным ID, `lastVersionId` и отдельным `gameDir`, сохранив неизвестные поля и остальные профили. Для живого Launcher: обнаружить закрытое состояние, создать backup только файла, который изменяется, записывать атомарно и восстановить backup при ошибке; никогда не читать/логировать учётные данные. Fabric version устанавливать закреплённой версией. Профиль включать только после готовности instance. Если формат, запущенный Launcher или вариант установки не позволяют доказать безопасную запись, **не редактировать профиль**: приложение показывает точные ручные шаги настройки Game Directory и не заявляет об автоматической активации. Зафиксировать поддержанный вариант и ограничение в README.

**Проверка:** smoke-проект на fixture-файлах профилей проверяет добавление/удаление только собственного профиля, сохранение чужих полей и rollback при ошибке; ручной прогон на реальном Launcher выполняется только после программной проверки и с проверкой Game Directory в UI Launcher. Если живой Launcher отсутствует, отметить этот тест как не выполненный, не как PASS.

### 6. Собрать простой WPF поток и опубликованный EXE

Один экран: название и закреплённые версии тестового релиза, целевой каталог, Install/Repair/Uninstall, прогресс, итог, открыть лог/отчёт, открыть Launcher или инструкцию ручной настройки. Не показывать неподтверждённые optional-моды или аппаратные пресеты. Во время операции запрещать повторный запуск несовместимого действия. Ошибки показывать без stack trace, полную диагностику — в лог. `README` объясняет, что это test pack, где находятся данные и как безопасно его удалить.

**Проверка:** build + smoke + self-contained publish из таблицы выше, затем открыть EXE и пройти UI до состояния ожидания установки; установить тестовый пакет в отдельный временный Game Directory и проверить локальный manifest, hashes и отсутствие изменений в vanilla `mods/config/saves`. Реальный запуск Minecraft и визуальное подтверждение профиля в Launcher отметить отдельно. Не объявлять тестовый релиз готовым для игроков без проверки игровых логов и запуска.

- [ ] WPF EXE собирается и запускается на Windows; `dotnet build`, smoke и `dotnet publish` завершились с кодом 0.
